### 4.5 深度探索：三种核心类型的实际结构（Admin-REST / Admin-GQL / Storefront-GQL）

> 更正说明：本节初版曾误判 ec20 租户下 Admin-REST、GQL Type 管理为"暂无数据"，实际是页面尚未加载完成就截图导致的假阴性。以下数字已用「等待加载完成 + 读取分页总数」的方式逐一复核，均为确认过的真实值。

切到 `ec20` 租户（电商核心业务租户）后和 `oneship`（物流业务租户）对比，数据分布差异很大：

| 类型 | oneship 租户条数 | ec20 租户条数 |
|---|---|---|
| Admin-REST | **328** 条 | **1013** 条 |
| Admin-GQL API | 0 条（暂无数据） | **226** 条 |
| Admin-GQL Type | 0 条（暂无数据） | **835** 条 |
| Storefront-GQL API | 0 条（暂无数据） | **231** 条 |
| Storefront-GQL Type | 0 条（暂无数据） | **801** 条 |
| Partner-GQL API | 0 条（暂无数据） | 13 条 |
| Function-GQL API | 0 条（暂无数据） | 0 条（暂无数据） |

修正后的结论：**oneship（物流）是纯 REST 租户，GQL 侧（Admin/Storefront/Partner/Function）全线为空**；**ec20（电商核心）是 REST + GQL 都在大规模使用的租户**，REST（1013 条）体量甚至超过 GQL 两端之和（226+231=457 条）。协议选型更像是跟着"业务本身的年龄/复杂度"走，而不是简单的"REST 只做回调、GQL 只做查询"——ec20 作为核心电商体系历史更久、集成方更多，REST 和 GQL 是并存演进而非互相替代的关系；oneship 作为相对垂直的物流业务，目前还没有引入 GQL 侧能力。

#### Admin-REST：API 定义 → 多环境实例 → 服务映射

以 ec20 的 REST API 详情为例，链路是三层：

1. **API 定义**（`/list` 页）：API 名称、描述、分组、API 路径、Http method。ec20 这 1013 条里能看到不少三方应用集成类接口（如「根据traceId查询函数入参」「查询账单关联用量接口」，分组 `partner-partner`）和建站类接口（如「获取评论数量」，分组 `建站域-博客评论`），说明 Admin-REST 承载的不只是内部管理，也包括面向合作方/第三方 App 的对外接口。
2. **API 实例列表**（点开 API 名称 → `/instance/{apiId}/{apiResultStyle}`）：一个 API 定义可以有多个「实例」，每个实例独立维护 test/pre/prod 三个环境的**发布状态**（已发布/未发布）和**灰度状态**，还有版本号（如 `v20210901`）、模式类型（`约定协议透传模式`）、更新人、运维监控入口（测试/生产US/生产SG 日志、实时监控、发布实时日志）。
3. **实例详情**（点「详情」→ `/instance-detail/...`）：基础信息定义（分组、**模式类型**：标准模式 / 约定协议透传模式二选一、API Path、是否对外发布文档、仅允许Enterprise访问、是否要分页）+ **入参信息**（"选择服务"——把这条外部 REST 路径映射到内部具体的后端服务方法，有"服务配置""自动映射字段"两个辅助按钮）。

关键概念：**API 定义与部署实例是解耦的**——同一个 API 可以在 test/pre/prod 各自独立发布、独立灰度，互不影响。

#### Admin-GQL：query/mutation 二分 + 按版本发实例 + Type 体系是真在用

创建 GQL API 的表单只有 4 个字段：**名称、分组、类型（query / mutation 二选一）、仅允许Enterprise访问（是/否）**——比 REST 定义简单得多，因为 GQL 没有 method/path 的概念，统一走一个 endpoint。

实例层同样存在（「API实例列表」），但是按**版本号**（如 `v20270301`）来组织，而不是像 REST 那样直接列实例；每个版本实例有环境状态、灰度状态、绑定权限、"历史是否发布过"等字段。

配套的 **Type 管理**（`/gql/type`）用于自定义 GraphQL 对象类型，创建时要选 **Kind**：`Object` / `InputObject` / `Enum` / `Connection` / `Union` / `Payload` / `Interface` / `Edge`（覆盖了标准 GraphQL 类型系统 + Relay 风格的 Connection/Edge/Payload 命名规范）。ec20 租户下 Admin-GQL Type 有 **835** 条、Storefront-GQL Type 有 **801** 条，规模跟对应的 API 数量（226/231）在同一量级——说明这套类型系统是被大量实际使用的核心基础设施，而不是摆设；oneship 租户 GQL 侧目前完全没有启用。

#### Storefront-GQL：真正面向店铺前台/消费者的业务 API

ec20 的 Storefront-GQL 231 条里能看到店铺前台的典型查询/操作，例如：

- `productVariant`（query，商品域-商品）
- `member4444`（query，会员域-店铺会员等级）
- `customerSmsMarketingSubscribe` / `customerEmailMarketingSubscribe`（Mutation，会员域-客户，短信/邮件营销订阅）
- `cartAttributeUpdate`（Mutation，交易域-购物车）

结构上 Storefront-GQL 跟 Admin-GQL 完全同构（同样是 名称+分组+类型query/mutation+权限 的定义方式，且各自配一套体量相当的 Type 系统），差别只在于**服务对象**：Admin-GQL 服务管理后台内部查询，Storefront-GQL 直接服务终端消费者在店铺前台看到的数据（商品、购物车、会员）。Partner-GQL 结构相同但数据量小得多（ec20 下仅 13 条），Function-GQL 在 ec20 下也是空的——这两个子域在电商核心业务里还处于早期/未大规模启用的阶段。

#### 约定协议透传模式的服务映射机制（以 oneship API `1688/4` 为例）

编辑一个约定协议透传模式的 REST API 实例，走 4 步向导：**基础信息 → 出入参设置 → 服务映射与错误码 → 其他设置**。

- 「出入参设置」这一步对约定协议透传模式来说非常简单，只有 API 实例名称/版本/描述，**不需要像标准模式那样逐字段定义 schema**——这就是"透传"的含义。
- **服务映射（核心机制）**：
  - 顶部有「是否开启多服务配置」总开关，开启后分「默认服务」「灰度服务」两个 tab，两边结构完全一样，可以让默认流量和灰度流量打到不同的后端服务。
  - 每个 tab 里"选择服务"：选服务类型（GRPC/HTTP/Dubbo）+ 具体服务方法，方法列表来自**基础数据 → 服务管理**这个全局服务注册表（后端团队把 gRPC/HTTP/Dubbo 方法注册在那，这里点"服务配置"就直接跳过去）。
  - 「自动映射字段」是最关键的功能：点开会弹出一张对照表——
    ```
    API入参坐标        →  服务入参坐标
    0.body.example_key →  0.req.exampleKey
    0.path.example_id  →  0.req.exampleId

    服务出参坐标         →  API出参坐标
    0.example.id        →  0.body.example.id
    0.example.sourceKey →  0.body.example.source_key
    0.link              →  0.header.link
    ```
    也就是根据所选后端服务的 IDL，一键生成"API 字段坐标 ↔ 服务字段坐标"的双向映射，还自动处理了驼峰/下划线的命名转换。点确定会**立即覆盖现有映射**，探索时需谨慎，只打开看一眼就取消，不要动真实配置。

> 已知小 bug（测试时留意）：编辑某个 API 实例时，「选择服务」面板里显示的 API 名称/路径有时对不上正在编辑的那个实例（页面状态没刷新干净），可能导致误映射。

## 观察小结

1. **多租户架构**：整个发布平台是多租户共享一套代码，登录后需选择租户（ec20 / 测试租户 / oneship / smartpush），每个租户各自维护独立的 API/GQL/Webhook 数据，但导航结构完全相同。
2. **API 管理是核心**，按客户端类型分 4 个子域（Admin/Storefront/Partner/Function），且只有 Admin 侧同时支持 REST + GQL，其余三个子域只走 GQL，指向「对外能力统一收敛到 GQL 协议」的设计取向。
3. **全生命周期链路清晰**：从「API管理」定义接口 →「审核管理」走审核流 →「发布管理」控版本/限流/灰度 →「协议管理」做路由映射和发布记录 →「文档管理」/「开发者模式」配套调试与查阅，形成一条完整的 API 发布流水线。
4. **MCP管理是新增能力**，与「开发者模式」下的 MCP调试工具配套，说明平台已经把 Agent 化能力（把已有 API 包装为 MCP 工具）纳入正式管理范畴，值得后续重点关注其测试覆盖。
5. **REST API 管理页体量较大**：oneship 租户下有 328 条 REST API 记录，涉及 oneship-logistics、oneship-onewarehouse、oneship-merchants 等多个业务分组；ec20 租户下更是达到 **1013** 条，是全平台目前已知数据量最大的单个列表页。
6. **不同租户的协议使用深度差异很大**（见 4.5，数字已复核修正）：物流租户 oneship 是纯 REST 租户（328 条，GQL 侧 Admin/Storefront/Partner/Function 全线为空）；电商核心租户 ec20 则是 REST 与 GQL 并重且都是大体量（Admin-REST 1013 条、Admin-GQL API 226 条+Type 835 条、Storefront-GQL API 231 条+Type 801 条、Partner-GQL 13 条），REST 体量甚至超过两端 GQL 之和——更像是业务历史长短/复杂度决定了协议栈的宽度，而非"REST 只做回调、GQL 只做查询"这种简单二分。
7. **API 定义与部署实例解耦**是 REST 和 GQL 共同的设计范式：定义一次，可以在 test/pre/prod 各自独立发布、独立灰度；REST 按"实例"直接列，GQL 按"版本号"组织实例。
8. **GQL 的 Type 体系是真实在用的核心基础设施**：Kind 支持 Object/InputObject/Enum/Connection/Union/Payload/Interface/Edge 等完整 GraphQL 类型系统；ec20 租户下 Admin-GQL Type 835 条、Storefront-GQL Type 801 条，与对应 API 数量（226/231）同一量级，说明字段结构管理被大规模使用；oneship 因为整体没上 GQL，Type 管理自然也是空的。
9. **测试用 API 有专门分组隔离**：顶部筛选栏「API 分组」下的「测试域-测试」分组专门存放测试用 API（oneship 52/328、ec20 149/1013），本模块后续新建的测试 API 一律挂在这个分组下，避免污染真实业务分组。
